# Design

## Context

See `proposal.md` for motivation and `specs/knowledge-retrieval/spec.md` for the behavior contract. 当前 Flask 应用使用 SQLite 保存 `materials` 和 `knowledge_entries`；每份材料只有一条完整正文记录。`GET /api/materials?q=` 只按标题筛选，材料预览和下载已按会话 `class_id` 限权。Compose 将 `./data` 挂载到 `/app/data`，应用以单个 Gunicorn worker 启动。

## Goals / Non-Goals

**Goals:**

- 以现有数据库中的材料正文为唯一权威来源，为关键词和语义检索建立可重建的派生索引。
- 在候选召回、融合及来源返回的全过程维持会话班级边界，并提供稳定到原材料片段的定位信息。
- 复用现有材料预览、下载授权和 Compose 数据持久化方式，覆盖既有材料和后续上传。

**Non-Goals:**

- 不生成检索答案、不提供聊天/RAG 对话，也不自动总结材料。
- 不改变上传权限和当前支持的 `.txt`、`.md` 格式，不增加跨班、跨学校或管理员检索。
- 不把向量索引作为原始材料的权威存储，也不依赖外部托管的向量数据库或在线 embedding API。

## Decisions

### 1. 独立的内容检索 API，与材料标题筛选保持兼容

- 新增登录保护的 `GET /api/knowledge/search?q=<query>&limit=<n>`；默认返回 10 条，最多 20 条。空白查询返回 `400`，无匹配返回 `200` 和空 `results`；未登录请求遵循现有 API 的 `401` 约定。服务端从会话获取班级，忽略或拒绝请求中的 `class_id`。
- 响应由 `results` 组成；每条包含 `snippet` 和 `source`（`material_id`、当前 `title`、`chunk_index`、`start_offset`、`end_offset`、受保护的预览/下载 URL）。偏移按原始 `body_text` 的 Unicode 字符计数，采用从 0 开始、右端不包含的区间。不要向客户端返回文件系统路径或跨类存储键。
- 工作区复用现有搜索区域展示内容检索片段和来源；`/api/materials?q=` 继续保留原有标题筛选语义，避免破坏现有 API 调用和测试。用户从结果打开现有材料预览时，定位或突出显示相应片段，正文仍以纯文本安全呈现。
- 考虑过直接改造 `/api/materials?q=`。选择独立端点是为了避免把标题列表过滤悄然改成片段检索，并使两种接口职责清楚。

### 2. SQLite FTS5 + 持久化 Chroma，采用混合排序

- 关键词召回使用 SQLite FTS5，对标题与片段正文建立 BM25 检索；中文内容在写入 FTS 前使用确定的中文分词器切词。语义召回使用嵌入式 Chroma 持久化向量，并采用可配置的本地中文 embedding 模型（建议初始模型 `BAAI/bge-small-zh-v1.5`）。模型路径、分块参数和索引版本必须配置化，便于替换和重建。
- 两路各取有界候选集后用 Reciprocal Rank Fusion（RRF）融合排名，避免直接比较量纲不同的 BM25 与 cosine 分数；同一材料中高度重叠的片段在最终集合中去重或限额。响应不暴露原始分数，避免将不可比的内部分值误作置信度。
- 向量元数据包含 `class_id`、`material_id`、稳定的 `chunk_id` 和索引版本。FTS 查询使用会话班级条件；Chroma 查询同时使用班级元数据过滤；融合后仍以 SQLite 对 `material_id`、`class_id` 和材料存在性进行权威复核。任何一路过滤失败或来源复核不通过时，候选均不得返回。
- 选择本地持久化向量库而非外部服务，适配单机 Compose 部署并避免向第三方发送课程正文。向量索引置于现有 `/app/data` 挂载下（例如 `/app/data/chroma`），模型缓存也持久化在该数据目录，避免容器重建时重复下载。无需新增独立服务容器。

### 3. 可复现分块和来源定位

- 以 `knowledge_entries.body_text` 中保存的 UTF-8 解码正文为基准；先按段落/Markdown 标题边界切分，再以可配置的字符上限（建议 600 个 Unicode 字符、相邻块重叠约 80 字符）形成片段，避免跨段任意截断。偏移始终指向原始 `body_text`，分词或 embedding 输入的规范化不得改变来源偏移。
- `knowledge_chunks` 保存 `chunk_id`、`material_id`、`class_id`、序号、原文偏移、原文片段及正文哈希。ID 按材料、分块版本和序号确定，使重试可幂等；返回标题时从 SQLite 当前材料记录读取，避免材料改名后引用旧标题。
- 搜索结果中的 `snippet` 必须是原文片段或其连续子串，且偏移对应同一原文。预览仍通过现有 `/api/materials/<id>`、下载通过 `/api/materials/<id>/download` 获取，不新增绕过班级检查的来源接口。

### 4. SQLite 为权威数据，索引为可修复投影

- 以新增的 chunk 元数据/索引状态表和 FTS5 虚拟表维护派生状态；材料及完整正文仍只以现有 SQLite 记录为准。首次升级及运维重建使用幂等 `scripts/rebuild_knowledge_index.py`，按内容哈希和分块/模型版本跳过未变材料，补齐旧记录、清理孤儿片段并重试失败项。
- 上传流程在两路索引都确认完成后才报告材料“可检索”；失败必须保留可识别、可重试的索引状态。重建任务能够从 SQLite 正文重新生成两路索引。删除材料时先以 SQLite 删除作为授权事实，清理 FTS/Chroma；即使向量清理暂时失败，检索的 SQLite 复核也会阻止失效结果泄露。
- Compose 启动时在数据库初始化后执行轻量 reconcile（只处理缺失、哈希变化或失败的材料），随后再启动 Gunicorn；不要在每次重启时无条件重算所有向量。模型首次下载时间可能较长，因此健康检查的启动宽限时间应覆盖首次初始化，或部署时预先缓存模型。
- 选择显式重建/恢复脚本，而非把向量库当作不可丢失数据；这利用已有 SQLite 与上传持久卷，回滚和备份边界更简单。对比方案是所有片段和向量都只放 SQLite；由于课程目标包含向量检索，保留 FTS5 + Chroma 组合以展示稀疏/稠密检索的职责差异。

### 5. 测试通过本地确定性数据验证相关性和隔离

- 检索单测对 embedding 接口使用固定向量/替身，不下载模型、不访问网络；另外提供本地模型可用时的可选烟雾测试。HTTP 测试至少覆盖正文关键词、同义/近义语义查询、A/B 班互不命中、伪造 `class_id`、未登录、空查询、结果定位/预览授权、上传后可搜、改名、删除、重建幂等和索引失败恢复。
- Compose 验收验证 `./data` 持久化向量目录；容器重建后查询仍成功，且不使用 `docker compose down -v` 清理持久数据。

## Risks / Trade-offs

- [本地 embedding 模型增加镜像/缓存体积、首次启动时间和 VM 内存/CPU 开销] → 将模型与缓存路径配置化并放入已持久化的数据卷，提供健康检查宽限；用小型中文模型，必要时允许从本地已缓存路径加载。
- [FTS5、向量库、SQLite 之间没有跨存储事务，故障可能造成索引短暂不一致] → SQLite 正文为权威源，维护可观测索引状态和幂等 reconcile；返回候选前用 SQLite 校验，失败来源绝不返回。
- [检索质量受分块、中文分词、embedding 模型影响] → 参数和模型版本化，覆盖关键词及语义基准样例；仅在显式重建时升级版本并核对命中片段与来源。
- [在单进程本地 Chroma 配置下横向扩容会引入并发与锁问题] → 本迭代沿用现有单 Gunicorn worker/单机 Compose 部署；多副本部署时另行评估独立向量服务，不在本次扩展。

## Migration Plan

1. 备份现有 `data/app.db` 与 `uploads/`；以新增表和 FTS 表进行向前兼容的数据库升级，不删除或重写原始材料正文。
2. 安装分词、embedding 和向量库依赖；配置本地模型及其持久缓存，Compose 继续使用 `./data:/app/data` 持久化数据库、FTS 元数据、Chroma 与模型缓存。
3. 运行幂等重建，对已有和种子材料生成片段与索引；校验班级分区、来源偏移、失败状态和重复执行结果后再启用检索 UI/API。
4. 若检索功能回滚，先停用新 API/UI 并恢复上一镜像；保留 SQLite 和上传目录。派生向量目录可备份后重建，不执行 `down -v` 或删除 `data/`、`uploads/`。
