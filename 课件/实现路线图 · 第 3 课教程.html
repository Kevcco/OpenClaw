2访问控制先于界面，每一步留下证据

会话与隔离先完成，界面后补；每一步都要留下同伴能复现的输出或截图。

知识点

失败路径优先于界面完善

未登录、学生上传、跨班按 ID，这三条判定系统是否真有访问控制。界面完备但用 curl 仍能绕过访问控制，本课不算完成。

4tasks.md 驱动：勾选就是进度

八步在 OpenSpec 里的落点就是 tasks.md：一条 task 一次循环，做完勾一项。

进度载体是 tasks.md，不是对话

Apply 阶段的进度只认一件事：tasks.md 里的待办框。第 2 课交付时每一条都写成- [ ] x.y 描述 — verify: 判据；本课完成一项，勾一项 - [x]。

verify 栏写的是可执行的判据（一条命令、一次接口调用、一次查库），不是装饰。勾选必须与 verify 的实际结果一致：没跑就勾，等于把进度变成无法复核的声明。

八步与 tasks.md 的对应

本页步骤 在 tasks.md 里应对应到 完成判据
1 骨架与配置 tasks.md §1 项目骨架与配置 导入与构建不报错；缺配置时启动失败
2 数据与种子 tasks.md §2 数据层与种子 双班与三个账号可查；两班标题可区分

本步要核对

核对项 本迭代应采用 怎么查（规约 / 代码 / 运行） 自检
本页每一步都能对应到本人 tasks.md 中的某条 task 吗？ 能。若存在无法对应的条目，只有两种可能：规约缺 task，或实现越界。 规约：tasks.md 的节与小节标题
代码：本轮实际改动的文件
运行：openspec status --change <change> 看完成度
勾选是否以 verify 结果为准？ 是。勾选与 verify 结果不一致，视为进度失真。 规约：verify 栏的判据
代码：提交说明里留的命令与输出
运行：任取一个已勾选项，按 verify 重跑一次

动手要做

  • 开工前用 openspec status --change <change> 确认四件套完成度，再用 openspec list 确认只有一个活动变更。
  • 每完成一项：执行该行 verify 并通过 → 勾选 - [x] → 提交。三件事在同一轮完成，不留到最后统一勾。
  • 把 verify 的命令与输出留在提交说明或迭代说明里，供同伴复核。

把否决理由用自己的话写进 design / 迭代说明；原文照录本表不算 ADR。
